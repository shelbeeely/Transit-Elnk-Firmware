ESP32 · E-ink · Battery

The departure board that doesn't stop at the edge of Wi‑Fi.

Firmware for a battery-powered 800×480 e-ink panel that shows when your bus actually leaves. It wakes on a timer, fetches, draws, and sleeps — and when the network is gone it falls back to cached data, then to the published timetable read straight off an SD card.

What it does

Built around one question: can I still catch it?

Everything here exists because a board that only shows raw times makes you do the arithmetic yourself — usually while walking, usually late.

Departures

Live countdowns

Minutes-until rather than clock times, with a real-time badge on predictions that came from the vehicle rather than the timetable.

Comparison

Scheduled beside real time

A live chip carries what the timetable promised, so 9m RT +4 sch 22:18 reads as four minutes late instead of just "later than you thought".

Planning

Home & Work trips

Save a fixed route chain with transfers. The board computes a leave-by time and tells you where and when to change buses.

Attention

Leave-now urgency

Departures five minutes out or closer get bold type and an outline — a glanceable cue rather than a number you have to parse.

Attention

Focus mode

Reduces the whole board to the one or two soonest departures, drawn large. Less to filter out when filtering is the hard part.

Sources

Two agencies at once

Transit API v4 for the main stop, plus optional Spokane Transit real-time arrivals shown alongside — not merged, so you can tell them apart.

Display

Portrait or landscape

The panel's native 800×480, or rotated to 480×800. Layout reflows; nothing is cropped.

Power

Wake, draw, sleep

No always-on radio and no always-on screen. E-ink holds the last frame with the panel powered down entirely.

Scheduled vs. real time

See the delay, not just the time

Transit's API has always sent a scheduled departure time alongside the live prediction. The board now shows both, leading with the delta because that's the part you act on.

A bus running early gets the same treatment as a late one, and arguably matters more — it's the one you miss by arriving on time.

Where it stays quiet: a departure with no real-time data shows no annotation, because the time on screen already is the schedule. Spokane Transit rows are exempt too — its feed carries a prediction with nothing to compare against, and claiming "on time" would be stating something false rather than omitting something unknown.

Preset trips

“Leave by 5:42, change at Division”

Configure the route chain you already know — bus 31, transfer to 32 — and the board resolves it against live departures every wake: when to leave, where to get off, and roughly when the connection goes.

It's deliberately not a general trip planner. You supply the route you actually take; the firmware answers the timing question against data it is already fetching, at zero extra API calls.

Focus mode

One thing, large

A toggle that drops everything except the next departure or two. Built for time-blindness: when the board is a wall of numbers, the useful one is harder to find than it should be.

Offline

Three sources, never confused for one another

Carry the board onto a bus and it leaves the network it was set up on. Rather than going blank, it steps down through what it still knows — and always says which of the three it is showing.

Live

Fetched this wake. The header reads Updated 22:13 and countdowns are current.

Cached

The last good fetch, restored from flash and marked Cached 2h ago. Departures that have already left are pruned out, so it empties rather than lying.

Timetable

The published schedule off the SD card. No delays, no cancellations — and no expiry either. This one keeps working a week into a trip.

The clock problem

No RTC chip, so it borrows one

The panel has no battery-backed clock. Time normally comes from the network each wake — which is exactly what you don't have offline, and without a clock there are no countdowns at all.

So before sleeping the firmware records the time and the sleep length into ESP32 RTC memory, which survives deep sleep, and adds them back on waking.

It stops before it lies. The sleep timer runs off an internal RC oscillator that isn't disciplined during sleep, so error accumulates. The firmware budgets a deliberately conservative bound, marks an estimated clock with a leading ~, and once the bound passes 15 minutes it goes back to reporting the time as unknown rather than showing a confident guess.

Offline long enough that the clock aged out: the cache is still drawn, but its age is reported as unknown rather than as fresh.

Expiry

A stale timetable says so

Transit agencies change service a few times a year, and past a feed's own validity window the schedule isn't merely old — it's wrong. The board reads that window off the card and names the date instead of printing times for trips that no longer run.

Holiday exceptions are applied too, so a Thanksgiving Thursday shows the Sunday timetable rather than a full weekday one.

Bus Wi-Fi

Signs itself in, then checks that it worked

Name an open network and an email or phone, and the board will associate to it, detect a captive portal with the same canary probes a phone uses, read the sign-in form off the page, and submit it.

It then re-probes, because portals return a cheerful 200 OK for rejected logins as readily as accepted ones. Only a clean canary counts as online.

Scope, honestly: this handles the “type your email, press Connect” shape. A portal that builds its form in JavaScript needs two values captured by hand, and one wanting a real username and password is out of scope. The board never joins an open network you haven't named.

Setup

No touchscreen, no keyboard, no app

On first boot the board hosts its own Wi-Fi access point and serves a setup page. Join it from a phone, the page opens itself, and each step is saved as soon as it's confirmed — so an interrupted setup resumes instead of starting over.

1

Pick a network

The board scans and lists what it can see, or you type an SSID directly.

2

Add an API key

Validated with a single live call, so a bad key fails here rather than as a blank board later.

3

Find your stop

Search by approximate coordinates and part of a name; pick from real results.

4

Done

The board draws its first frame and drops into its normal wake cycle.

Settings, later

A long press of the power button at boot reopens the same portal with the options that aren't part of first-run setup.

Orientation, and the POSIX time zone that decides which day's timetable to read.

B

Optional second data source, keyed by the number printed on the stop sign.

C

Home & Work

Build each leg: route, boarding stop, direction, transfer stop. Directions are confirmed against live data.

D

The open network to fall back on, and what to hand its sign-in page.

Specifications

What it runs on

BoardXteink X4 — ESP32-C3, SSD1677 controller
Display800×480 e-ink, 4-level greyscale
OrientationLandscape (native) or portrait, switchable at runtime
StorageNVS for settings and the offline cache; optional SD card for full static GTFS
TimeSNTP when online; RTC-memory estimate offline. No RTC chip on this board.
InputPower button only — no touch, no keyboard. Setup runs over a captive portal.
DataTransit API v4; optional Spokane Transit GTFS-RT and static GTFS
Refresh60 minutes by default, treated as a floor, with an optional overnight sleep window
API budgetOne call per wake — about 720 a month at the default, against a 1,500/month free tier
ToolchainPlatformIO / Arduino-ESP32, built on the FreeInk SDK
Tests231 host-side tests, plus a real cross-compile, on every push

No battery-life figure here on purpose. Nobody has measured one on real hardware yet. The design is wake-fetch-draw-sleep with the panel and peripheral rails powered down between refreshes, but an unmeasured number dressed up as a spec would be a guess.

Before you build one

What it doesn't do

Every project has these. Here they are up front rather than in an issue tracker.

The offline timetable is Spokane-only

Transit's API has no static feed to download, so a non-STA stop has the cache and nothing beyond it. The mechanism is general; the data isn't.

You need your own API key

Transit reviews access requests by hand, and there's no published turnaround. Start that before you order hardware.

TLS certificates aren't pinned

HTTPS connections currently skip verification. Fine on a home network, worth fixing before leaning on the bus Wi-Fi feature.

Timetable cards need regenerating

Roughly three times a year, when the agency changes service. The board tells you when, but you still have to do it.

Captive portals only go so far

Email-or-phone sign-in works. Real usernames and passwords, vouchers and JavaScript-built forms don't.

No hardware has run this yet

It cross-compiles in CI and 231 host tests pass, but the panel-facing paths — SD, deep sleep, battery ADC — haven't been exercised on a physical board.

Getting started

Build it

Two commands, once PlatformIO is installed. The host test suite needs no ESP32 toolchain at all.

# clone, with the FreeInk SDK submodule
$ git clone --recursive https://github.com/shelbeeely/Transit-Elnk-Firmware
$ cd Transit-Elnk-Firmware
$ pip install -U platformio

# host-side tests — no hardware, no toolchain download
$ pio test -e native

# the real firmware (downloads an ESP32 toolchain the first time)
$ pio run -e xteink_x4

Optional: the offline timetable

Generate the SD card's static GTFS from a current feed, then copy it across.

$ python3 tools/gen_sta_tables.py <path-or-url-to-gtfs.zip>
$ cp -r sd_card_data/sta /media/<your-card>/
