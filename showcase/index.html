Answers one question, from across the room.

Firmware for a battery-powered e‑ink departure board. It tells you when to leave — not when the bus is scheduled — and it keeps answering when the network is gone.

A wall board should not need unlocking.

Checking a transit app takes a phone, an unlock, a load, and a list to read. That is a lot of steps for a question you ask twice a day on your way out of the door.

So this is a panel by the door that already knows. It wakes on a timer, fetches, draws, and sleeps — and because e‑ink holds an image with the power off, the board is readable the whole time the chip is asleep.

The harder half is what happens when the network goes. Most connected displays become a blank rectangle the moment they lose Wi‑Fi, which is exactly when you have picked the thing up and taken it somewhere. This one steps down through what it still knows, and is always explicit about which of those it is showing you.

What it does

Tells you when to leave

Save the route chain you already take — the 31, change to the 32 — and the board works out a leave‑by time from live departures, including the walk to the stop and a buffer for the transfer. It names the stop you change at and roughly when the connection goes.

It is not a general trip planner. You supply the route you actually ride; the firmware answers the timing question against data it is already fetching, which is why it costs no extra API calls.

Shows how late it actually is

A live chip carries the time the timetable promised alongside the prediction, so 9m RT +4 sch 22:18 reads as four minutes behind rather than just later than you hoped. A bus running early gets the same treatment, and matters more — it is the one you miss by turning up on time.

Gets loud when it matters

Anything five minutes out or closer goes bold and picks up an outline. No colour to rely on, no animation to miss — just weight, which is all a four‑tone panel has to work with.

Strips down to one thing

A focus mode that drops everything except the next departure or two, drawn as large as the panel allows. Built for time‑blindness: when the board is a wall of numbers, the useful number is harder to find than it should be.

Sets up from a phone, with no app

There is no touchscreen and no keyboard. On first boot the board hosts its own Wi‑Fi network and serves a setup page; a phone joins it and the page opens itself. Each step saves as it is confirmed, so an interrupted setup resumes instead of starting again.

Three answers, and it never confuses them.

Carry the board onto a bus and it leaves the network it was set up on. Rather than going blank it steps down — and the header always says which rung it is standing on.

Live

Fetched this wake

Real‑time predictions, current countdowns, the usual board.

Cached

The last good fetch

Real departures, clearly aged. Anything that has already left is pruned out, so the cache empties instead of lying.

Timetable

The published schedule

Read off an SD card: the whole service day, holidays included. No delays, and no expiry on its usefulness either.

Including the clock

The panel has no battery‑backed clock, so time normally arrives over the network — the one thing you do not have offline, and without it there are no countdowns at all. The firmware writes the time and the sleep length into the chip's RTC memory before sleeping and adds them back on waking.

That estimate drifts, so it is bounded and labelled: an estimated clock shows a leading ~, and once the accumulated error passes fifteen minutes the board goes back to reporting the time as unknown rather than showing a confident guess.

How it's built

The interesting constraints were memory, power, and having no hardware to test on.

TargetESP32‑C3 driving an SSD1677 e‑ink panel, 800×480 at four grey levels, on PlatformIO and Arduino‑ESP32 over the FreeInk SDK.
Testable by designEvery module splits into pure logic and a thin hardware shim, so parsing, filtering, trip planning, calendar maths and layout all run on the host. 231 tests, plus a real cross‑compile, on every push.
A timetable in 2.6 MB222,598 stop_times rows packed into a custom binary format sorted by stop and time, so a lookup is a lower‑bound binary search into the stop's block and then a second search inside it — about a kilobyte read for a typical stop.
Time done properlyGTFS measures departures from noon minus twelve hours rather than midnight. That distinction only bites on the two daylight‑saving days a year, and getting it wrong puts every evening bus an hour out. Tests cover both days.
Inside the free tierOne API call per wake regardless of how much is configured — preset stops ride along in the same batched request. About 720 calls a month against a 1,500 limit.
Rendered proofEvery screenshot on this page is generated: board frames by driving the real renderer in the test suite, setup pages by loading the exact HTML the firmware serves into a headless browser. They cannot drift from the product.

What isn't done

Stated here rather than discovered later.

No hardware has run it

It cross‑compiles in CI and the host suite passes, but the panel‑facing paths — SD, deep sleep, the battery ADC — have never touched a physical board.

No battery figure

The design is wake, draw, sleep with the rails down in between. Nobody has measured how long that lasts, so there is no number here.

The offline timetable is one agency

Spokane Transit publishes a static feed; the Transit API does not offer one to download. The mechanism is general, the data is not.

TLS certificates aren't pinned

Connections currently skip verification. Acceptable on a home network, worth fixing before leaning on the public‑Wi‑Fi path.
